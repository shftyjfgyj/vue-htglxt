## 新增页面：运营分析 `/analytics`

菜单为顶级项，权限 `dashboard:view`（`010_m15_analytics.sql`，幂等 upsert）。

### 1. 审核效能（需 `article:audit` 或 `comment:audit`）

`GET /api/v1/analytics/moderation?days=7|30|90`

数据来自 `audit_records`（`decision` / `operator_type` / `operator_id` / `created_at`）：

- KPI：累计审核记录、**自动化率**（机器处置占比）、人工处置次数、**待审积压**（文章 + 评论）
- 审核量趋势：按天堆叠柱（机器判定 / 人工处置）
- 决策分布：五种 `decision` 的占比条
- 审核员处理量：按 `operator_id` 聚合的处理次数 + 通过/驳回数

这是全站级内部指标，所以**不跟着页面权限走**：服务端单独要求审核类权限，
前端 `canAudit` 为假时整块不渲染。实测 viewer 直接调接口得 **403**。

### 2. 标签共现图谱

`GET /api/v1/analytics/tag-graph?limit=30`

`article_tags` 自连接（`t2.tag_id > t1.tag_id` 去重成对），只统计**已发布**文章；
节点大小映射标签热度，边粗细映射共现次数，力导向布局、可拖拽缩放。
两端不同时存在于节点集合的边会被过滤，避免 ECharts 画出孤立端点。

### 3. 兴趣画像

`GET /api/v1/analytics/interest?limit=8` —— 固定本人数据。

`article_view_logs` / `article_likes` / `article_favorites` 三表 `UNION`（去重）后按分类聚合，
按「读过的**不同**文章数」计，避免同一篇既读又赞又收藏被算三次。

**降级处理**：雷达图至少要三条轴才成立，分类少于 3 个时前端自动退化为条形列表。
当前开发库只有 2 个分类，所以实际走的是条形分支。

### 4. 作者排行榜

`GET /api/v1/analytics/author-ranking?period=week|month|all&limit=10`

按 `浏览×1 + 点赞×3 + 评论×2` 加权排序；周/月榜用 `COALESCE(publish_at, created_at)` 过滤
（`publish_at` 可能为空，回退到 `created_at`）。

## 已知边界

- 审核效能没有「平均审核时长」：现有表没有记录「内容提交时间」，
  用 `articles.updated_at` 近似会在多次编辑后失真，宁可不做也不给错数。
  若确实需要，得先给 `articles` / `comments` 补一个 `submitted_at`。
- 标签图谱在标签稀少的库上会很稀疏（当前 3 节点 1 边），数据量上来后才有观赏性。
- 兴趣画像是「涉猎广度」而非「投入深度」——因为 `article_view_logs` 是每人每篇只留最近一次的
  upsert 结构，没有阅读次数与时长可用。
