# 交付说明 · M14 趣味性增强（成长 / 互动 / 质量体检）

回应「功能趣味性单调」：不是功能少，而是**很多数据已经在库里、却从没被展示过**。
这一批优先做「零 schema 变更 + 立刻有反馈」的三块。

## 1. 创作热力图 + 成就徽章（A）

**数据来源**：`articles.created_at`、`article_tags` —— 全部实时计算，**不新增任何表**。

- 后端新增 `modules/growth/`：
  - `GET /api/v1/growth/heatmap?days=365` → 每日发文数 + 总产出、活跃天数、**当前连续 / 历史最长连续**
  - `GET /api/v1/growth/achievements` → 11 枚徽章（创作 / 影响力 / 坚持三组），带 `current`/`target` 进度
  - 数据边界固定为**本人**，不需要任何新权限点
- 前端：`components/HeatmapChart.vue`（ECharts 日历热力图，按需引入 `CalendarComponent` + `VisualMapComponent`），
  看板新增「我的创作热力图」与「成就徽章」两张卡；徽章按「已解锁优先 → 完成度倒序」排列，并提示「下一个」目标。
- 连续天数口径：今天没写但昨天写了**不算断**（当天尚未结束）；`computeStreaks` 用 UTC 天数序号比较，避开夏令时。

## 2. 评论点赞 + 神评 + @提及（D）

这是唯一动 schema 的一块（`009_m14_comment_interaction.sql`，幂等）：

- 新表 `comment_likes`（唯一键 `(comment_id, user_id)` 保证幂等）
- `comments.like_count` 反范式计数（与 `articles.like_count` 同一套路，避免列表每次聚合）
- `comments(article_id, like_count)` 索引支撑热度排序

接口与交互：

- `POST/DELETE /api/v1/comments/:id/like`，重复点赞不会重复计数（`INSERT IGNORE` + 计数只在 `affectedRows>0` 时变更）
- 评论树带 `likeCount` / `liked`；点赞用**乐观更新**，失败回滚并提示
- 顶层评论支持「按时间 / 按热度」切换（**仅当顶层评论 ≥ 2 条时出现**，回复保持原时间顺序以免上下文错乱）
- 获赞最多且 **≥ 3 赞**的评论挂「🔥 神评」标记
- **@提及**：解析正文里的 `@昵称`（最多 5 个、去重），命中用户走现成的 `notify()` 发 `mention` 通知。
  正则带 `(?<![\w.])` 负向后顾，避免把邮箱 `a@b.com` 当成提及；
  已经因为「评论了文章 / 回复了评论」收到通知的人不再重复打扰。
- `notifications.type` 是 `varchar(30)`，新增 `mention` 类型无需改表。

## 3. 文章质量体检分（E）

`modules/article/article.quality.ts`：**纯函数**，7 个维度共 100 分——

| 维度 | 满分 | 口径 |
| ---- | ---- | ---- |
| 标题 | 15 | 8~30 字最佳，过短/过长递减 |
| 摘要 | 10 | 40~120 字最佳 |
| 正文篇幅 | 25 | 去 HTML 后按字数分档（≥800 满分） |
| 段落结构 | 15 | 块级标签切分计数；整篇一段的长文重扣 |
| 配图 | 10 | 有封面满分；仅正文有图 7 分 |
| 分类 | 10 | 已选即满分 |
| 标签 | 15 | 2~5 个满分，超过 5 个反而扣分（主题被稀释） |

- `POST /api/v1/articles/quality-preview`（不落库，字段全可选，边写边算）
- `GET /api/v1/articles/:id` 详情里也带 `quality`，打开已保存文章立刻有分
- 编辑器右侧新增「质量体检」面板：分数环（conic-gradient，深浅色主题通用）+ 7 条维度进度条
  + 只列出**未满分**项的改进建议；400ms 防抖，请求失败静默保留上次结果，不打断写作
- 分数**不参与**任何审核判定，审核仍由 moderation 引擎负责

## 5. 已知边界

- 成就不记录「首次达成时间」（不新增表），只表达已达成 + 还差多少；若要发「解锁通知」需要落一张表。
- 徽章的「创作」类指标统计的是**已发布**文章数，草稿不计入。
- `article_view_logs` 是「每人每篇只保留最近一次」的 upsert 结构，因此**阅读时段分布 / 年度报告**这类需要完整阅读历史的功能，
  必须先新增 append-only 的读取事件表，否则算出来是错的。
