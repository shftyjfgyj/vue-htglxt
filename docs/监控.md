# 监控与告警（M6）

## 1. 暴露的端点

| 端点 | 用途 | 说明 |
| --- | --- | --- |
| GET /health | 就绪探针 | 带数据库探活，DB 不可用返回 503 |
| GET /health/live | 存活探针 | 只判断进程存活，不查库 |
| GET /metrics | Prometheus 指标 | 设置 METRICS_TOKEN 后需 x-metrics-token 请求头 |

## 2. 指标清单

| 指标 | 类型 | 标签 | 用途 |
| --- | --- | --- | --- |
| http_requests_total | counter | method, route, status | 请求量；route 已归一化（/api/v1/articles/:id）避免基数爆炸 |
| http_request_errors_total | counter | method, route, status | 4xx/5xx 错误量 |
| http_request_duration_seconds | histogram | method, route | 耗时分布，桶 10ms~5s，可算 P95/P99 |
| app_business_events_total | counter | event | 登录成功/失败、审核通过/驳回、导入导出等业务事件 |
| process_uptime_seconds / process_resident_memory_bytes / nodejs_heap_used_bytes | gauge | — | 进程健康度 |
| app_db_pool_connections | gauge | — | 连接池当前连接数 |

## 3. 接入 Prometheus

```bash
# 1) 抓取配置（示例见 docker/prometheus-scrape.yml），scrape_interval: 15s
# 2) 告警规则（示例见 docker/alert-rules.yml）
# 3) 校验并热加载
promtool check rules /etc/prometheus/rules/htglxt.yml
curl -X POST http://localhost:9090/-/reload
```

内置告警规则：API 掉线、错误率 > 5%、P95 > 1s、Node 堆 > 400MB、10 分钟内登录失败 > 50 次（疑似暴力破解）、长时间无流量。

## 4. Grafana 看板建议

1. 流量与错误：sum(rate(http_requests_total[5m])) by (route) + 错误率曲线。
2. 延迟：P50/P95/P99（histogram_quantile）。
3. 业务：increase(app_business_events_total[1h]) by (event)。
4. 资源：进程内存、堆内存、连接池连接数。

## 5. 日志

- 采用 pino 结构化 JSON 日志，每条请求含 traceId，可通过响应头 X-Trace-Id 关联前后端。
- 慢请求（默认 > 1000ms，SLOW_REQUEST_MS 可调）会额外打 warn 日志，字段含 method/path/status/durationMs。
- 生产建议：容器场景用 stdout 交给日志驱动；PM2 场景已配置 logs/api-*.log，配合 logrotate 按天切割、保留 14 天。
- 审计日志（operation_logs / login_logs）落在数据库，与运行日志互补：前者回答「谁改了什么」，后者回答「服务怎么了」。

## 6. 排障速查

| 现象 | 先看 |
| --- | --- |
| 接口 5xx | /metrics 的 route 维度错误率 → 用响应头 traceId 搜日志 |
| 接口变慢 | 慢请求 warn 日志 → 对应 route 的 P95 → 检查 SQL 与索引 |
| 登录异常 | app_business_events_total 中 event=login_failed 的曲线 + login_logs 表 IP 分布 |
| 内存上涨 | nodejs_heap_used_bytes 趋势；确认是否有大导出/大导入并发 |
| 数据库连接耗尽 | app_db_pool_connections 接近 DB_CONNECTION_LIMIT |
