# 交付说明 · M13 文章越权修复（editor 改写他人文章）

## 1. 问题

`editor`（内容编辑）在**全站文章**列表里对任意一行的「编辑」按钮可用，
且接口放行，能直接改写、删除、提交审核、回滚他人文章版本。

实测复现（修复前）：

```
editor 登录 → PUT /api/v1/articles/60   # 文章 60 的作者是 admin
HTTP 200  文章已更新（旧内容已存档为版本 1）   # 真的写库并产生了版本快照
```

## 2. 根因

| # | 位置 | 问题 |
| - | ---- | ---- |
| 1 | `article.service.ts` `isContentManager()` | 判定条件为 `*` 或 `article:audit`，而它同时被用于「可见范围」与「改写他人文章」两件事。editor 持有 `article:audit`（审核台），于是绕过了所有权校验 |
| 2 | `article.bulk.service.ts` | 同一判定抄了一份（`article:audit`），批量删除同样能绕过 |
| 3 | `moderation.service.ts` | 又叫 `isContentManager`，口径是 `article:manage` **或** `article:audit`——三处三样 |
| 4 | `002_seed.sql` | 给 editor 的授权是「article 模块全给」，天然包含 `article:audit`；`007_m11.sql` 又追加 `article:manage` |
| 5 | `ArticleListView.vue` | 「编辑 / 提交审核 / 删除」只判断权限码，不看文章归属，全站列表每行都渲染 |

其中 #1 与本仓库 M11 文档「服务层 `isContentManager` 应以 `article:manage` 判定」的约定不符。

## 3. 修复（按确认的策略：editor 保留查看与审核，改写他人文章收归 admin）

**后端**
- 新增 `modules/article/article.access.ts`，把两个概念拆开并收敛为唯一实现：
  - `canViewAllContent` = `*` \| `article:manage` \| `article:audit` → 列表/详情可见范围、导出范围、复制
  - `canManageOthersContent` = `*` \| `article:manage` → 编辑、删除、提交审核、版本恢复、回收站恢复
- `article.service.ts` / `article.bulk.service.ts` 全部改走这两个函数（含原先内联在 `deleteArticle` 里的第三份判定）
- `article.routes.ts` 审核记录接口放行 `article:audit`，审核台能力不受影响
- `moderation.service.ts` 的私有函数更名 `isTrustedReviewer`（只关「可信度」，行为不变），消除同名歧义

**数据库（`npm run db:migrate` 可重复执行）**
- `002_seed.sql`：editor 的模块级授权排除 `article:manage`
- `007_m11.sql`：editor 的 `article:manage` 改为显式回收（幂等兜底历史库）
- `007_m11.sql`：「全站文章」菜单 `permission_code` 由 `article:manage` 改为 `article:audit`

**前端**
- `ArticleListView.vue`：「编辑 / 提交审核 / 删除」改为「本人文章 或 持有 `article:manage`」才显示
- `ArticleEditView.vue`：直接敲 `/content/articles/:id/edit` 也校验归属，不是自己的稿子跳 403
- 「审核 / 发布 / 下线」保持按权限码显示（editor 的审核台职责不变）

**新建用户角色必选**
- `UserView.vue` + `user.schema.ts`：`roleIds` 必填且至少一个，避免建出「能登录但零权限」的账号

## 4. 验证

修复后接口实测（editor = 文章 60 的非作者）：

| 操作 | 结果 |
| ---- | ---- |
| `GET /articles/60`（查看） | 200 ✅ 仍可查看 |
| `PUT /articles/60`（编辑） | **403 只能编辑自己的文章** ✅ |
| `DELETE /articles/60`（删除） | **403 只能删除自己的文章** ✅ |
| `POST /articles/batch` 删除 [60] | `skipped: 1`，`reason: 无权操作他人文章` ✅ |
| `PUT /articles/1`（自己的稿子） | 200 ✅ 不受影响 |
| `POST /articles/60/audit` | 400（权限放行、状态不符）✅ 审核权保留 |
| `GET /articles/60/audit-records` | 200 ✅ 审核记录可看 |
| `GET /menus` | 仍含「全站文章」，无「系统管理」✅ |

自动化：
- `npm --prefix apps/server test` → **29 passed**（`article-access.test.ts` 11 项、`user-schema.test.ts` 4 项回归防护）
- `npm --prefix apps/server run typecheck` / `npm --prefix apps/web run typecheck` → 均通过

数据库终态：editor 的 article 权限为 `audit/create/delete/detail/list/publish/update`（**无 `manage`**）；
菜单 3 的 `permission_code = article:audit`。

## 5. 补充修复：前端权限快照过期（第二层）

第一层改完后，**已在线的浏览器仍能看到「编辑」按钮**。原因是前端把登录那一刻的
`user.permissions` 持久化在 `localStorage`，而路由守卫只在 `store.user` 为空时才拉 profile：

```ts
// 修复前：localStorage 里有 user 就永远不刷新
if (!store.user) { await store.fetchProfile(); }
```

于是管理员改了角色/权限后，该浏览器不重新登录就永远按**旧权限**渲染按钮。
对本次 bug 而言，用户的浏览器里仍存着含 `article:manage` 的旧快照，所以按钮照旧显示。

用 Playwright（系统 Edge）实测确认：

| 会话 | 他人文章的「编辑」按钮 |
| ---- | ---- |
| A 全新登录（权限来自服务端） | 不显示 ✅ |
| B 复用 localStorage 旧快照（含 `article:manage`） | **显示** ❌ ← 复现报告现象 |

**修复**

1. `stores/user.ts` 新增 `profileFresh`（不持久化，每次页面加载重置为 false）；
   `router/index.ts` 守卫改为**每次页面加载强制刷新一次 profile**，保证「一次加载 = 一份真实权限」。
   这同时修掉了**所有**基于本地权限的按钮/菜单过期问题，不只是文章这一处。
2. 编辑页的判定不再依赖本地权限缓存：`GET /articles/:id` 现在由服务端下发
   `canEdit`（`canEditOwnArticle`：本人或持有 `article:manage`），
   `ArticleEditView.vue` 直接按 `data.canEdit === false` 跳 403。

**复验（Playwright + Edge）**

| 场景 | 结果 |
| ---- | ---- |
| A 全新登录 → 他人文章 | 无「编辑」按钮 ✅ |
| B 旧权限快照（含 `article:manage`）→ 他人文章 | 无「编辑」按钮 ✅（启动刷新纠正） |
| C 旧权限快照 + 直接敲 `/content/articles/60/edit` | 落地 `/403` ✅ |
| 服务端 `canEdit` 字段 | `false` ✅ |

> 权限模型澄清：`article:update` 是**动作**权限（`PUT /:id` 路由把门），
> `article:manage` 是**范围**权限（服务层所有权校验把门）。
> 「能改他人文章」= 两者兼具；只给 `article:manage` 不足以放行写接口。

## 6. 已知边界

- `editor` 仍可**查看**全站文章与审核记录，这是审核台职责所需（`article:audit`）。
- 批量操作对混合选中（自己的 + 他人的）按行返回错误，由后端逐条拦截，不做整批拒绝。
- 若日后需要「可改写他人文章但不是 admin」的角色，给该角色 `article:update`（动作）+ `article:manage`（范围）即可，无需改代码。
